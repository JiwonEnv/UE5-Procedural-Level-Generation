# 🤔 언제 쓰나

## 절차적 맵 생성이란

맵의 **구조 자체**(방이 어떻게 이어지는지, 복도와 문의 위치)를 알고리즘이 매번 새로 조립하는 방식입니다. 물건 위치나 몬스터 경로만 바꾸는 "내용물 랜덤"과는 다릅니다.

| 단계 | 무엇이 바뀌나 | 예시 |
|---|---|---|
| ① 고정 맵 + 내용물 랜덤 | 구조는 고정, 물건 · 경로 · 잠긴 문만 바뀜 | 직접 만든 맵에 랜덤 요소 추가 |
| ② **모듈 조립형 (이 프로젝트)** | 미리 만든 방 모듈을 매번 다른 연결로 조립 | Enter the Gungeon |
| ③ 완전 생성형 | 벽과 바닥까지 알고리즘이 생성 | 로그라이크 던전 |

## 언제 선택하는가

| ✅ 선택한다 | ❌ 선택하지 않는다 |
|---|---|
| 같은 공간을 여러 번 플레이하는 구조 (수거형 협동, 로그라이크) | 연출 순서가 중요한 공간 (특정 방에서 클라이맥스) |
| 맵 구조를 외우는 순간 긴장감이 사라지는 장르 | 한 장면의 완성도가 목적인 경우 (포트폴리오 샷, 시네마틱) |
| 제작 인력에 비해 맵 볼륨이 많이 필요할 때 | 동선을 정밀하게 설계해야 하는 퍼즐 · 스텔스 레벨 |
| 방 단위로 콘텐츠를 계속 추가할 계획이 있을 때 | 일정이 짧아 생성기와 검증에 시간을 쓸 수 없을 때 |

## 장단점

| 장점 | 단점 |
|---|---|
| 매번 구조가 달라 반복 플레이가 강해진다 | 직접 연출한 장면을 원하는 순서로 보여주기 어렵다 |
| 방 모듈을 추가할수록 맵이 늘어난다 | 동선의 긴장 흐름(입문 → 위기 → 클라이맥스)을 보장하기 어렵다 |
| 맵을 외워서 생기는 지루함이 없다 | 조합마다 동선 · 계단 · AI 경로가 깨질 수 있어 테스트량이 크다 |
| 모듈 규격이 정해지면 아트 작업을 병렬로 나누기 쉽다 | 생성기 · 겹침 검사 · 내비메시 · 네트워크 동기화에 개발 시간이 든다 |
| | 베이크 조명을 쓰기 어렵고 동적 조명 비용이 든다 |

> 이 프로젝트는 단점 두 번째(긴장 흐름)를 **시작 · 허브 · 끝 방 고정**으로, 세 번째(테스트량)를 **200시드 자동 검사**로 줄입니다.

## 관리 원칙

| 원칙 | 내용 | 이 프로젝트에서 |
|---|---|---|
| **규격 문서가 단일 기준** | 그리드 · 문 소켓 · 층 높이 · 피벗 규칙은 문서 하나로 관리하고, 모듈은 그 규격으로만 검사한다 | [모듈 규격](05-모듈-규격) · 규격 위반 시 경고 |
| **시드 재현성** | 같은 시드는 언제나 같은 맵. 버그 리포트에는 시드를 함께 남긴다 | 로그 `seed N: M modules` · `-plgseed=N` |
| **모듈 카탈로그** | 방 목록과 속성(크기 · 문 · 역할 · 가중치)을 데이터로 관리한다 | 생성기의 `Modules` 배열 |
| **자동 검증** | N회 생성해 실패율 · 막힌 경로 · 겹침을 측정하고, 모듈을 바꾸면 다시 돌린다 | [검증과 디버그](06-검증과-디버그) |
| **디버그 시각화** | 소켓 · 경계 · 연결 그래프 · 시드를 화면에 표시한다 | 모듈 이름 라벨 (`bShowLabels`). 나머지는 예정 |
| **성능 예산** | 맵당 방 수, 동시 로드 방 수, 동적 조명 수의 상한을 정한다 | `RoomCount` · `MaxHalfExtent` 5,000cm |

## UE5 도구 비교

| 도구 | 잘하는 것 | 이 프로젝트에서의 역할 |
|---|---|---|
| Level Instance · Packed Level Actor | 방을 하나의 단위로 묶어 배치 | 실제 방 모듈 (예정) |
| Level Streaming | 런타임에 레벨을 불러오고 내림 | 생성된 방 로드 (후보) |
| PCG Framework | 규칙 기반 산포 · 배치 | 방 안의 장식 · 소품 배치 (후보) |
| **커스텀 C++ 생성기** | 방 연결 그래프와 규칙 | **생성 알고리즘 본체** |
| 외부 플러그인 | 구현 시간 절약 | 사용하지 않음 (직접 구현이 목적). 비교 대상으로만 조사 |
